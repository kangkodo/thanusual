# Crossgate — AI 교차검수 파이프라인 규칙

> 설계 원본: `crossgate-spec` v1.13.3. 이 파일은 실행용으로 압축한 규칙이다. 규칙을 바꾸려면 명세와 킷을 함께 개정한다.

## 1. 단계와 역할

| 단계 | stage 값 | 작업 | 검수 | 판정 |
|---|---|---|---|---|
| 요청 정리 | `request` | Master(Claude) | 사용자(`질문` 결정이 있을 때만) | APPROVED |
| 기획 | `plan` | Master(Claude) | Codex `plan-reviewer` (읽기 전용) | APPROVED / REJECTED |
| 개발 | `dev` | Codex `developer` | Claude `crossgate-reviewer` (읽기 전용) | APPROVED / REJECTED |
| 독립 QA | `qa` | Codex `qa` | Master가 증거 표본 확인 | PASSED / FAILED |
| Wiki | `wiki` | Master(Claude) | Codex `wiki-reviewer` (읽기 전용) | APPROVED / REJECTED |

- 사용자는 Master하고만 대화한다. Codex는 Master가 `crossgate codex <역할>`로 호출하는 도구다.
- 작업 AI와 검수 AI는 항상 다른 모델이다.
- 검수 AI는 읽기 전용이다. 판정을 Master에게 돌려줄 뿐이고, 기록은 Master가 `crossgate verdict`로 한다.
- 지시 파일(작업 지시·검수 요청·QA 지시)은 `## 읽을 것`으로 시작한다: 대상 파일, 관련 문서의 경로·절, 이전 산출물. 역할 AI는 이 목록부터 읽고, 목록 밖 방향 잡기(문서 색인, 인수인계 문서 등)는 목록으로 판단이 안 될 때만 한다.
- 기준의 우선순위: `request.md`(사용자 결정) > `todo.md`(기획) > 현재 코드. 코드는 지금 구현된 사실이지 원하는 동작의 근거가 아니다. 위쪽이 틀리거나 비어 보이면 편한 쪽으로 해석하지 않고 Master에게 올린다(R12).

### 요청 정리: 결정 목록

기준은 질문 수가 아니라 "사용자가 정할 결정을 AI가 대신 고르지 않았는가"다. 뒤에 검수가 있다고 이 단계를 덜 하지 않는다. 늦게 드러난 결정은 반려·상한·사용자 대기로 돌아온다.

1. 이번 작업이 건드리는 대상(데이터, 화면, 사용자 유형, 외부 시스템)을 적고, 대상마다 그리고 대상끼리 만나는 곳마다 답해야 할 결정을 뽑는다. 목록은 넓게, 질문은 좁게 한다.
   - 구조: 개수·관계·식별 (하나인가 여럿인가)
   - 동작: 생성→변경→종료, 동시에 일어날 때, 실패·예외. 두 개념이 만나는 곳("취소 가능" + "결제 있음" → 취소하면 결제는?)
   - 기술: 저장·전달 방식, 일관성
   - 계약: 상태값 집합, 고유성, 응답 필드, 기존 계약·이전 버전과의 호환
   - 완료 증명: 무엇을 어디까지 확인하면 끝인가. "문제없게"처럼 엄격함이 요구되면 검증 범위도 사용자 결정이다
   맞는 관점이 없는 중요한 결정이 보이면 관점을 늘린다. 입력이 짧을수록 더 넓게 찾는다.
2. 결정마다 이 순서로 처리를 정해 `request.md` 결정 목록에 적는다.
   1. 사용자가 말했거나 목표·제약·코드 사실에서 나온다 → `사용자` / `도출`. 근거를 적고 묻지 않는다.
   2. 이미 정해진 방식 안의 조정값이고 사용자가 선호를 가질 이유가 없다 → `조정값`. 기본값을 적고 묻지 않는다.
   3. 둘 다 아니다 → `질문`. AI가 고르면 추측이다.
   중요한 관점이 이번 작업에 해당하지 않으면 `해당 없음`과 이유를 남긴다. 조용히 빼지 않는다.
3. `질문`만 묻는다. 어디에 해당하는지, 왜 아직 정해지지 않았는지, 정하지 않으면 무엇이 달라지는지를 댈 수 있어야 질문이다. 영향이 큰 것부터 추천안과 함께 묻는다. 기술 결정은 선택지·장단점·추천을, 제품·업무 규칙은 구체안과 "다른 생각이 있다"는 열린 선택지를 낸다.
4. 답을 결정 목록과 "사용자 확인 기록"에 적는다. 답이 건드린 주변만 한 번 다시 훑는다. 사용자가 결정을 미루면 그대로 적고, 그 결정에 기대는 일은 범위에서 뺀다.

## 2. 판정 규칙

| # | 규칙 |
|---|---|
| R4 | 차단 지적(루브릭 X) 0건, 미검증 0건이면 승인. 권고는 승인을 막지 않는다 |
| R6 | 반려하면 지적마다 위치(`파일:라인` 또는 문서 절), 문제, 기대 상태를 적는다 |
| R7 | 승인하면 "확인한 항목" 목록을 적는다 |
| R8 | 단계별 루브릭 항목을 빠짐없이 O / X / 미검증으로 판정한다 |
| R10 | 차단 지적에는 ID를 붙인다(`P-n` 기획, `D-n` 개발, `Q-n` QA, `W-n` Wiki). 같은 문제는 회차가 바뀌어도 같은 ID |
| R11 | 요구 위반과 회귀는 권고로 낮추지 않는다 |
| R12 | 원인이 요구 자체의 오류·누락이면 기획 단계로 돌려보낸다 |
| R13 | 환경 장애면 BLOCKED. 확인 못 한 루브릭 항목은 미검증. 둘 다 승인이 아니다 |
| R14 | 재검수는 이전 지적과 그 뒤 바뀐 부분만 본다. 새 차단 지적은 바뀐 부분과 그것이 영향을 주는 곳에서만 낸다. 바뀌지 않은 곳의 새 문제는 요구 위반·회귀일 때만 차단이고 나머지는 권고다 |

## 3. 루브릭

| 단계 | 항목 |
|---|---|
| 기획 | ① 요구 대응 ② 범위 경계(하지 않을 일 명시) ③ 상태 계약(상태·경계값·예외) ④ 검증 가능성(수용 기준이 실행 가능하거나 관찰 방법이 있음) ⑤ 영향 문서(영향받는 문서 / 갱신 불필요 사유) ⑥ 결정 근거(request 결정 목록의 `사용자`·`도출`·`조정값` 처리가 적힌 근거로 뒷받침되고, 기획이 목록에 없는 사용자 결정을 조용히 정하지 않음. 진짜 조정값과 코드에서 다시 알아낼 구현 세부는 지적하지 않는다) |
| 개발 | ① TODO 구현 ② 근거 일치 ③ 범위 준수 ④ 부작용(기존 계약·테스트를 깨지 않음) |
| QA | ① 수용 테스트 통과 ② 시나리오 수행(정상·실패 흐름) ③ 증거 존재(캡처·로그) |
| Wiki | ① 관련성 ② 정확성(코드와 일치, 다른 문서와 모순 없음) ③ 비관련 불변 ④ 목차·링크(`docs/INDEX.md`가 실제 문서와 일치, 표준 Markdown 상대 링크만) |

## 4. 검수 응답 형식 (검수 AI 공통)

첫 줄은 반드시 `판정: 승인` / `판정: 반려` / `판정: BLOCKED` 중 하나다.

```
판정: 반려
복귀 단계: 기획 | 개발
루브릭: 요구 대응 O / 범위 경계 O / 상태 계약 X / 검증 가능성 O / 영향 문서 O / 결정 근거 O
차단 지적:
  P-1 위치: docs/todo.md DEV-003
      문제: ...
      기대: ...
해결 확인: P-0 해결 (재검수일 때 이전 지적별 해결 / 미해결 / 재발)
확인한 항목:
  - ...
권고:
  - ...
```

재검수(2회차부터, R14):
- Master는 요청에 이전 차단 지적(ID·위치·기대)과 바뀐 부분을 넣는다. 개발은 `git diff <이전 검수 커밋>..HEAD`, 기획·Wiki는 바뀐 항목(DEV ID·절) 목록이다. 전체 diff·문서 경로는 참고로 함께 준다.
- 검수 AI는 이전 지적의 해결 / 미해결 / 재발부터 판정한다. 이전 회차에서 O였고 이번 변경이 닿지 않은 루브릭 항목은 다시 읽지 않고 `O(유지)`로 적는다.

## 5. 반복 상한과 조정 요청

- 단계당 검수는 최초 포함 3회까지다(`config.cap`). QA에서 개발로 돌아와도 횟수는 초기화하지 않는다.
- 3회째에도 승인이 아니거나, 같은 지적 ID가 3회 연속 검수에서 남아 있으면 멈춘다. Master는 `ESCALATED`를 기록하고, 두 AI의 주장을 나란히 사용자에게 보여준다.

## 6. 버전 고정과 기록

- 승인과 PASSED는 커밋된 상태에서만 기록한다(`ai-log/` 제외). 판정 레코드의 `commit`이 곧 검수한 버전이다.
- `crossgate verdict`만 `verdicts.jsonl`에 쓰고, `timeline.md`는 자동 생성한다.
- `crossgate codex`와 `crossgate claude`는 호출마다 토큰·시간(Claude는 비용 포함)을 `usage.jsonl`에 덧붙인다(커밋 대상). 이 파일에 줄이 덧붙는 것은 보호 경로 위반이 아니다.
- 설치된 킷 복사본(`.crossgate/kit/`)은 `MANIFEST.sha256`으로 봉인된다. `gate`와 `merge-check`는 봉인이 깨지면 실패한다.
- 개발 역할이 `todo.md`에서 체크와 "완료 근거" 줄만 바꾼 것은 보호 경로 위반이 아니다. `gate`가 자동 판별한다. 문구가 바뀌면 위반이다.
- 개발 역할을 부르기 전에 Master가 지시 파일까지 커밋한다(정식 모드에서 `crossgate codex`는 `ai-log`에 커밋하지 않은 변경이 있으면 멈춘다). 호출 뒤 `crossgate gate --protect-since <그 커밋>`으로 보호 경로 변경을 잡는다. 호출 출력과 게이트 로그는 git에서 제외되는 `raw/`에 둔다.
- 현재 실행(`.crossgate/current-run`)은 설치 위치 하나에 하나다. 다른 세션이 `init-run`을 하면 바뀌므로, Master는 `init-run` 뒤의 모든 명령에 `--run <실행 폴더>`를 붙인다. `init-run`은 최근 60분 안에 쓰인 실행을 바꿀 때 경고하고, `verdict`는 기록한 실행 이름을 출력한다.
- `raw/`와 `03-qa/captures/`는 git에서 제외하고, `crossgate clean-raw`로 기한(기본 30일)이 지나면 지운다. 저장 전 비밀값을 마스킹한다.

## 7. 병합 위임 (조건을 전부 만족하면 자동 병합)

`crossgate merge-check`가 판정한다.

1. 필수 단계의 최종 판정이 모두 승인/PASSED이고, 개발·QA·Wiki 승인이 현재 코드와 같은 버전이다
2. 고정층 검사(`crossgate gate`)와 기존 CI가 통과했다 (CI 필수 검사)
3. 금지 경로(`config.forbidden`)를 건드리지 않았다
4. `ESCALATED` 기록이 없다
5. 미검증이 남은 승인이 없다

하나라도 걸리면 Master가 사용자에게 병합 여부를 묻는다. 자동 병합 뒤에는 한 줄 보고(무엇이 병합됐는지, 증거, 되돌리는 방법)를 보낸다.

## 8. 배포

자동 배포는 없다. 사용자가 지시할 때만 `crossgate deploy`로 미리보기를 보여주고, `--yes`로 실행한다.

## 9. 설치와 업그레이드

- 새 프로젝트: 전역 스킬 `/crossgate-setup`(설치 명령 `install.sh --global`)이 적용 전 점검 → 설치 → 설정 → CI까지 진행한다.
- 새 버전: 프로젝트에서 `/crossgate 업그레이드`. 원본 위치는 설치 때 git이 무시하는 `.crossgate/local.json`(`kit_source`·`kit_remote`)에 기록된다. 개인 경로가 들어가므로 커밋하지 않는다.

## 10. 작업 등급

작업의 무게에 맞춰 거치는 단계와 추론 강도를 나눈다. 등급은 작업을 시작할 때(`init-run` 전) Master가 근거와 함께 추천하고 사용자가 확정한다(두 모드 공통). AI 혼자 낮추지 않는다.

| 등급 | 기준 | 필수 단계 | 진행 |
|---|---|---|---|
| 가벼움 `light` | 스타일·문구·배치만 바뀐다. 데이터·API·상태 흐름 변화 없음. 저장소 하나 | request, dev | 요청 한두 줄(결정 목록은 `질문`이 있을 때만), TODO 없음. Codex 구현 → gate → 바뀐 화면 전후 캡처 → Claude 검수. 둘 다 낮은 강도 |
| 보통 `standard` | 기존 기능의 동작 조정. 설계는 사용자와 확정. 저장 데이터·API 계약·권한은 그대로 | request, dev | 결정 목록 → TODO(기획 검수 없음) → 개발 → 개발 검수. 개발 검수에 결정 목록을 넘긴다. TODO의 영향 문서는 Master가 `roles/wiki-writer.md`대로 고쳐 같은 diff로 검수받는다 |
| 무거움 `full` | 기능 추가·삭제, 저장소 둘 이상, 저장 데이터·API 계약·권한·인증, 동작이 바뀌면 안 되는 넓은 리팩터 | request, plan, dev, qa, wiki | 전체 과정. 기획 실수를 코드에서 발견하면 개발 왕복이 여러 번 들어 기획 검수를 넣는다 |

- 실행은 `init-run <slug> --route light|standard|full`(기본 full). 필수 단계와 역할별 추론 강도는 `config.routes`(없으면 킷 기본값)를 따르고, `codex`·`claude` 호출은 현재 실행의 등급에서 강도를 읽는다. 한 번만 바꾸려면 `--effort`.
- 승격: diff가 금지 경로·API·스키마·마이그레이션·권한을 건드리거나, 검수나 캡처에서 의도하지 않은 동작·화면 변화가 드러나면 한 등급 올린다. Master가 `crossgate route <올린 등급>`으로 현재 실행의 등급을 올리고(기록이 `meta.json`에 남는다) 사용자에게 알린 뒤, 건너뛴 결정 목록·TODO·검수를 보충한다. 낮추기는 사용자 확인 뒤 새 실행으로만 한다.
- 가벼움의 전후 캡처는 바뀐 화면과, 공유 스타일을 고쳤다면 그 스타일을 쓰는 대표 화면까지 찍는다. 바뀐 요소가 실제로 보이는 상태로 찍는다(접힌 시트·메뉴는 펼치고, 화면 밖이면 스크롤한다). 요소가 보이지 않는 캡처는 증거가 아니다. 캡처 경로를 검수 요청의 읽을 것에 넣는다.
- 보통에서 구현이 결정 목록에 없는 사용자 결정을 조용히 정했으면 개발 검수가 범위 준수 X와 "복귀 단계: 기획"(R12)을 적는다.
- 0.4 이하의 `--quick`은 `--route standard`와 같다. 옛 설정(`required_stages`·`quick_stages`)도 읽는다.

## 11. PM 모드 (작업공간)

git이 아닌 루트 아래 저장소가 여러 개이고, 작업 절차는 작업공간 자체 규칙이 이미 정해 둔 경우에 쓴다. 크게는 엔진(역할 호출·읽기 전용 검수·판정 기록·사용량·봉인)만 제공한다.

- 설치: `install.sh --workspace <루트>`. 스킬·안내 단락·`.gitignore`·CI는 건드리지 않는다. 설정은 `mode: "pm"`과 `repos`(저장소별 `gate`·`protected`, 폴더명이 다르면 `path`).
- `codex`·`gate`·`verdict`에 `--repo <이름>`. 개발·QA 역할은 `--repo`가 필수이고 쓰기는 그 저장소 안으로 제한된다(실행 기록 폴더도 못 쓴다. 완료 근거는 답변으로 받고 Master가 옮긴다).
- 검수 역할은 루트에서 읽기 전용으로 돈다(여러 저장소를 함께 본다).
- 스킬이 설치되지 않으므로 Master는 작업공간 규칙을 따른다. 작업공간 규칙이 요청 정리·재검수·지시 파일 형식을 따로 정하지 않았다면 이 문서(1장 요청 정리, R14, 읽을 것)를 따른다. 작업공간 규칙(AGENTS.md 등)에서 `.crossgate/kit/CROSSGATE.md`를 가리켜야 Master가 이 규칙을 읽는다.
- 승인·PASSED는 `--repo`를 주면 그 저장소의 커밋에 묶이고, 저장소가 없는 판정(요청·기획)은 버전에 묶지 않는다.
- `merge-check`는 없다. 병합·배포는 작업공간 규칙을 따른다. 루트가 git이 아니므로 `ai-log/`는 버전 관리되지 않는다.
