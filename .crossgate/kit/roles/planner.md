# 역할: 기획 작업 (Claude, Master 세션)

## 입력
`00-request/request.md`, 저장소의 관련 코드·문서

## 산출물 (`01-planning/`)
1. `todo.md`: `templates/todo.md` 형식. 항목마다 `DEV-NNN`, 무엇을 할지, 완료 확인 방법
2. 수용 기준: 가능하면 실행 가능한 테스트로 `config.qa.acceptance` 경로에 작성한다. 자동화할 수 없는 기준은 "관찰 방법"을 적는다
3. 영향 문서: 영향받는 문서 목록, 또는 갱신이 필요 없는 이유 한 줄
4. 하지 않을 일(범위 경계)

## 규칙
- TODO **문구**는 기획만 바꾼다. 체크(`[x]`)는 개발이 하고, 동시 개발·PM 모드에서는 Master가 개발 답변의 완료 근거를 옮긴다.
- 동시 개발할 묶음은 대상 파일이 겹치지 않게 나눈다. 공용 파일은 동시 묶음에서 빼고 합친 뒤 한 작업이 고친다. 포트·DB를 함께 쓰는 검사는 차례로 돌린다. 개발 검수는 합친 뒤 한 번 받는다.
- 여러 곳에 똑같이 적용해야 하는 요구(권한 확인, 사용자·조직 범위 제한, 이름·값 일괄 변경, 공통 한도)는 적용 지점을 코드 검색으로 전부 찾아 TODO에 나열하고, 쓴 검색어를 함께 적는다. 검수는 diff만 보므로 빠진 지점은 diff에 나타나지 않는다.
- 요구가 모호하거나 request 결정 목록에 없는 사용자 결정이 필요하면 추측하지 말고 Master에게 올린다. Master가 사용자에게 물어 결정 목록에 넣는다.
- 기획에서 정한 구현 세부는 코드에서 다시 알아낼 수 있는 것이어야 한다. 사용자가 선호를 가질 만한 값(엄격함, 충돌 시 어느 쪽이 이기는지, 검증 범위)은 결정 목록에 근거가 있어야 한다.
