# AI 교차검수 파이프라인 규칙

> 설계 원본: `ai-crossreview-pipeline-spec` v1.5. 이 파일은 실행용으로 압축한 규칙이다. 규칙을 바꾸려면 명세와 킷을 함께 개정한다.

## 1. 단계와 역할

| 단계 | stage 값 | 작업 | 검수 | 판정 |
|---|---|---|---|---|
| 요청 정리 | `request` | Master(Claude) | 사용자(새 가정이 있을 때만) | APPROVED |
| 기획 | `plan` | Master(Claude) | Codex `plan-reviewer` (읽기 전용) | APPROVED / REJECTED |
| 개발 | `dev` | Codex `developer` | Claude `pipeline-reviewer` (읽기 전용) | APPROVED / REJECTED |
| 독립 QA | `qa` | Codex `qa` | Master가 증거 표본 확인 | PASSED / FAILED |
| Wiki | `wiki` | Master(Claude) | Codex `wiki-reviewer` (읽기 전용) | APPROVED / REJECTED |

- 사용자는 Master하고만 대화한다. Codex는 Master가 `pipeline codex <역할>`로 호출하는 도구다.
- 작업 AI와 검수 AI는 항상 다른 모델이다.
- 검수 AI는 읽기 전용이다. 판정을 Master에게 돌려줄 뿐이고, 기록은 Master가 `pipeline verdict`로 한다.

## 2. 판정 규칙

| # | 규칙 |
|---|---|
| R4 | 차단 지적(루브릭 X) 0건, 미검증 0건이면 승인. 권고는 승인을 막지 않는다 |
| R6 | 반려하면 지적마다 위치(`파일:라인` 또는 문서 절), 문제, 기대 상태를 적는다 |
| R7 | 승인하면 "확인한 항목" 목록을 적는다 |
| R8 | 단계별 루브릭 항목을 빠짐없이 O / X / 미검증으로 판정한다 |
| R10 | 차단 지적에는 ID를 붙인다(`P-n` 기획, `D-n` 개발, `Q-n` QA, `W-n` Wiki). 같은 문제는 회차가 바뀌어도 같은 ID |
| R11 | 요구 위반과 회귀는 권고로 낮추지 않는다 |
| R12 | 원인이 요구 자체의 오류·누락이면 기획 단계로 돌려보낸다 |
| R13 | 환경 장애면 BLOCKED. 확인 못 한 루브릭 항목은 미검증. 둘 다 승인이 아니다 |

## 3. 루브릭

| 단계 | 항목 |
|---|---|
| 기획 | ① 요구 대응 ② 범위 경계(하지 않을 일 명시) ③ 상태 계약(상태·경계값·예외) ④ 검증 가능성(수용 기준이 실행 가능하거나 관찰 방법이 있음) ⑤ 영향 문서(영향받는 문서 / 갱신 불필요 사유) |
| 개발 | ① TODO 구현 ② 근거 일치 ③ 범위 준수 ④ 부작용(기존 계약·테스트를 깨지 않음) |
| QA | ① 수용 테스트 통과 ② 시나리오 수행(정상·실패 흐름) ③ 증거 존재(캡처·로그) |
| Wiki | ① 관련성 ② 정확성 ③ 비관련 불변 |

## 4. 검수 응답 형식 (검수 AI 공통)

첫 줄은 반드시 `판정: 승인` / `판정: 반려` / `판정: BLOCKED` 중 하나다.

```
판정: 반려
복귀 단계: 기획 | 개발
루브릭: 요구 대응 O / 범위 경계 O / 상태 계약 X / 검증 가능성 O / 영향 문서 O
차단 지적:
  P-1 위치: docs/todo.md DEV-003
      문제: ...
      기대: ...
해결 확인: P-0 해결 (재검수일 때 이전 지적별 해결 / 미해결 / 재발)
확인한 항목:
  - ...
권고:
  - ...
```

## 5. 반복 상한과 조정 요청

- 단계당 검수는 최초 포함 3회까지다(`config.cap`). QA에서 개발로 돌아와도 횟수는 초기화하지 않는다.
- 3회째에도 승인이 아니거나, 같은 지적 ID가 3회 연속 검수에서 남아 있으면 멈춘다. Master는 `ESCALATED`를 기록하고, 두 AI의 주장을 나란히 사용자에게 보여준다.

## 6. 버전 고정과 기록

- 승인과 PASSED는 커밋된 상태에서만 기록한다(`ai-log/` 제외). 판정 레코드의 `commit`이 곧 검수한 버전이다.
- `pipeline verdict`만 `verdicts.jsonl`에 쓰고, `timeline.md`는 자동 생성한다.
- `pipeline codex`는 호출마다 토큰·시간을 `usage.jsonl`에 남긴다(커밋 대상). Claude 측 사용량은 아직 수집하지 않는다.
- 개발 역할이 `todo.md`에서 체크와 "완료 근거" 줄만 바꾼 것은 보호 경로 위반이 아니다. `gate`가 자동 판별한다. 문구가 바뀌면 위반이다.
- 개발 역할을 부르기 전에 Master가 먼저 커밋한다. 호출 뒤 `pipeline gate --protect-since <그 커밋>`으로 보호 경로 변경을 잡는다.
- `raw/`와 `03-qa/captures/`는 git에서 제외하고, `pipeline clean-raw`로 기한(기본 30일)이 지나면 지운다. 저장 전 비밀값을 마스킹한다.

## 7. 병합 위임 (조건을 전부 만족하면 자동 병합)

`pipeline merge-check`가 판정한다.

1. 필수 단계의 최종 판정이 모두 승인/PASSED이고, 개발·QA·Wiki 승인이 현재 코드와 같은 버전이다
2. 고정층 검사(`pipeline gate`)와 기존 CI가 통과했다 (CI 필수 검사)
3. 금지 경로(`config.forbidden`)를 건드리지 않았다
4. `ESCALATED` 기록이 없다
5. 미검증이 남은 승인이 없다

하나라도 걸리면 Master가 사용자에게 병합 여부를 묻는다. 자동 병합 뒤에는 한 줄 보고(무엇이 병합됐는지, 증거, 되돌리는 방법)를 보낸다.

## 8. 배포

자동 배포는 없다. 사용자가 지시할 때만 `pipeline deploy`로 미리보기를 보여주고, `--yes`로 실행한다.

## 9. 경로

- 정식 경로: 기본값. 필수 단계는 `config.required_stages`.
- 간단 수정 경로: 사용자가 명시할 때만(`init-run --quick`). 필수 단계는 `config.quick_stages`. 금지 경로를 건드리면 정식 경로로 승격하고 건너뛴 검수를 보충한다.
